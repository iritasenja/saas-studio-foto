# 4. Tenant isolation

Ini bagian paling penting.

Setiap tabel bisnis memiliki:

```sql
tenant_id uuid not null references public.tenants(id)
```

Contoh:

```text
customers
├── id
├── tenant_id   ← pembatas tenant
├── full_name
├── email
└── phone
```

Sehingga:

```text
Studio A
tenant_id = AAA
```

hanya boleh membaca:

```text
customers
where tenant_id = AAA
```

Sedangkan:

```text
Studio B
tenant_id = BBB
```

tidak akan bisa membaca data Studio A.

RLS memang dirancang Supabase untuk memberikan pembatasan row-level seperti ini. ([Supabase][1])

---

# 5. Role tidak dibuat global

Saya memilih:

```text
tenant_members
------------------------
tenant_id
user_id
role
```

Contoh:

```text
Budi
│
├── Studio A → photographer
│
└── Studio B → admin
```

Ini lebih tepat daripada:

```text
profiles
└── role = photographer
```

karena role seseorang adalah **konteks terhadap tenant**, bukan atribut global user.

Jadi RLS nantinya bisa melakukan:

```text
auth.uid()
      ↓
tenant_members
      ↓
tenant_id + role
      ↓
akses data
```

# 6. RLS policy

Semua tabel exposed sudah:

```sql
alter table ... enable row level security;
```

Kemudian policy dasar menggunakan:

```sql
public.is_tenant_member(tenant_id)
```

yang secara konsep berarti:

```text
Apakah user yang sedang login
merupakan member aktif
dari tenant ini?
```

Untuk operasi tertentu tersedia:

```sql
public.has_tenant_role(
    tenant_id,
    roles[]
)
```

misalnya:

```sql
public.has_tenant_role(
    tenant_id,
    array['owner','admin']::public.member_role[]
)
```

Jadi kita sudah punya fondasi untuk membangun permission lebih detail nanti.

# 7. Tenant creation dibuat atomic

Saya juga memperbaiki satu bagian penting dari desain awal.

Jangan membiarkan frontend melakukan:

```text
INSERT tenants
INSERT tenant_members
INSERT studio_profiles
```

secara terpisah.

Karena bisa terjadi:

```text
tenant berhasil
↓
membership gagal
↓
tenant yatim
```

Sebagai gantinya schema menyediakan:

```sql
create_tenant(
    p_name,
    p_slug
)
```

yang melakukan:

```text
create tenant
      ↓
create owner membership
      ↓
create studio profile
      ↓
return tenant_id
```

dalam satu database transaction.

Ini juga membuat onboarding SaaS nantinya jauh lebih mudah.

# 8. Index

Index utama sudah disiapkan berdasarkan pola query yang kemungkinan besar sering digunakan.

Contohnya:

```text
tenant_members
    tenant_id + role
    user_id + tenant_id

bookings
    tenant_id + starts_at
    tenant_id + status
    tenant_id + customer_id

customers
    tenant_id + full_name
    tenant_id + phone

production_tasks
    tenant_id + status
    tenant_id + production_order_id

payments
    tenant_id + paid_at
```

Prinsipnya hampir semua query operasional akan diawali dengan:

```sql
where tenant_id = ...
```

sehingga `tenant_id` menjadi bagian penting index.

## 10. Satu keputusan arsitektur yang saya rekomendasikan

Untuk tahap ini **jangan dulu menggunakan custom JWT claim untuk role tenant**.

Supabase memang mendukung custom claims/RBAC, tetapi kasus kita berbeda karena:

```text
1 user
   ↓
bisa punya banyak tenant
   ↓
dan role berbeda di setiap tenant
```

Jadi lebih aman dan sederhana untuk fondasi:

```text
JWT
 │
 └── auth.uid()
          │
          ▼
    tenant_members
          │
          ├── tenant_id
          └── role
```

Custom claims bisa dipertimbangkan kemudian apabila kebutuhan authorization sudah lebih kompleks. Supabase sendiri mendokumentasikan custom claims sebagai salah satu pendekatan RBAC, bukan satu-satunya pendekatan. ([Supabase][2])

# 2.3 Membuat Tenant pertama

Nah, ini bagian yang mungkin sedikit membingungkan.

Kita **tidak perlu memasukkan tenant secara manual ke tabel `tenants`**.

Schema kita sudah menyediakan function:

```sql
public.create_tenant(
    p_name,
    p_slug
)
```

Function tersebut dirancang untuk:

```text
create tenant
      ↓
buat tenant_members
      ↓
jadikan user sebagai owner
      ↓
buat studio_profiles
      ↓
return tenant_id
```

Ini memang sudah ada di schema yang kamu jalankan. 

Tetapi ada satu hal:

`create_tenant()` menggunakan:

```sql
auth.uid()
```

Artinya function tersebut harus dipanggil oleh **user yang sudah login**, bukan sembarang SQL Editor session.

Jadi **jangan jalankan function itu dari SQL Editor untuk sekarang**.

Kita akan memanggilnya nanti dari Nuxt setelah Supabase Auth terpasang.
